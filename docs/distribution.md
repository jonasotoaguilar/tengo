# Distribution — Tengo

Preparation only. No EAS project is linked, nothing has been built by
EAS, and nothing has been uploaded to any store. The pipeline that
actually runs today is still the source-only GitHub release
(`.github/workflows/release.yml` on tag `v*`): a `git archive`
tarball plus the unsigned `expo export` bundle. Everything below that
involves EAS, signing, or Google Play is a documented next step, not
a working pipeline.

## What exists now

- `eas.json` (hand-written, never generated by `eas init`): Android-only
  build profiles — `development` (development client, internal
  distribution, APK), `preview` (internal distribution, APK), and
  `production` (Android app bundle, the format Google Play requires
  for new apps). `cli.appVersionSource` is `local`, so the version
  lives in `app.json` and EAS reads it from there.
- `app.json` release fields: `version` (`1.0.0`, matching
  `package.json`, which is what `release.yml` tags) and
  `android.versionCode` (`1`, integer, bumped manually per upload
  because no remote version counter exists yet).
- `__tests__/distribution-config.test.ts`: the contract guard. It
  proves the profile set, the local versioning, the typed release
  fields, the absence of committed credential-shaped values, and that
  `release.yml` stays source-only.
- Deliberately absent: no `submit` block in `eas.json`, no EAS
  project id, no `owner`, no service-account key, no keystore. There
  is nothing here that can upload, and that is intentional.

## Release process end to end

### Today (works without any credentials)

1. Bump `version` in `package.json` and `app.json` together (the
   contract test enforces they match) and bump
   `android.versionCode` by at least 1.
2. Tag `v<version>` and push the tag. `release.yml` checks out the
   exact tag revision, runs typecheck, lint, format check, the Jest
   suite, and an unsigned Android export smoke, then attaches the
   source tarball and the export bundle to the GitHub release.
3. The tag must equal `v<package.json version>`; anything else fails
   closed and no release is published.

### Someday (needs the user's credentials and decisions below)

4. The user links an EAS project (`eas init` against their Expo
   account) and records the project id in `app.json` (`extra.eas`)
   — this step has NOT been done and needs their login.
5. The user creates the app in Google Play Console, completes the
   content declaration, and links a service account (Play Console →
   Setup → API access) with release permissions for the chosen
   track. The JSON key stays out of the repo (EAS Secrets or a local
   file on `.gitignore`); only then does a `submit` block belong in
   `eas.json`.
6. `eas build -p android --profile production` produces the app
   bundle; `eas submit -p android` uploads it to the chosen track.
   Neither command has ever been run here.

## What the user has to provide and decide

- **Expo account + EAS project link.** Requires `eas login` and
  `eas init` with the user's credentials. Not done here: there are
  no credentials in this environment and nothing was uploaded.
- **Google Play service-account credentials.** A Play Console
  service account with release permission on the chosen track, kept
  as an EAS secret or a gitignored local key file — never committed.
- **Upload-key ownership.** Either let Google Play App Signing hold
  the signing key (EAS creates the upload key on first upload; the
  upload key can be reset if compromised) or manage a keystore
  independently. Undecided — see below.
- **First-submission checklist** (Play Console, all user-side):
  create the app listing, complete the app-content declaration,
  set up the store listing below, complete the content-rating
  questionnaire, set pricing and distribution, then configure the
  service account.

## Listing metadata draft

Draft for the Play Console store listing. No marketing claim beyond
what the product does; placeholders are marked as such.

- **App title:** Tengo — Household Inventory
- **Short description (≤ 80 chars):** Offline household inventory by
  location, in English and Spanish.
- **Full description:**
  Tengo keeps track of what your household owns and where it is:
  items with per-location stock, locations, and categories, in
  English or Spanish. Everything is stored in the app's own database
  on your device and the app works fully offline. There are no
  accounts, no servers, and no analytics: your data never leaves
  your device through this app. Deleting anything always asks for
  confirmation first.
- **Category:** Lifestyle (to confirm at listing time).
- **Support contact:** [PLACEHOLDER — support email or URL required
  before any submission]
- **Privacy story (what the app can honestly say):** no account, no
  backend, no analytics, no network call in any product flow; data
  stays in the app's own on-device database (`tengo.db`). The only
  device permissions are the ones the app already declares: the
  camera (barcode scanning) and notifications (stock/expiry
  reminders). This says nothing about OS-level backup behavior,
  which is unknown and must not be promised.
